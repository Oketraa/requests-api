Практические примеры поиска ошибок по логам (LogQL)

Ниже приведены основные сценарии анализа логов и примеры запросов на языке **LogQL** в панели *Grafana Explore* для быстрого поиска и локализации неисправностей. Чтобы посмотреть все логи, необходимо перейти в панель *Grafana Drilldown*, в разделе *Logs*.

---

### Пример 1. Сквозной поиск по Request ID (Трассировка цепочки запроса)
**Сценарий:** Клиент (фронтенд или утилита `curl`) получил ошибку выполнения запроса. Для диагностики используется уникальный UUID запроса, возвращенный сервером в HTTP-заголовке `X-Request-ID`.

* **Запрос в Grafana (LogQL):**
    ```logql
    {project="deploy"} |= "9835789e61a21783a7ae6730bcfb190e"
    ```
* **Результат анализа:** Лог-система выводит полную хронологическую цепочку обработки этого запроса всеми компонентами системы:
    1.  Строка от `service="nginx"` показывает время прилета запроса на прокси, внешний IP клиента, метод, URI (`/api/requests/7`) и User-Agent.
    2.  Строка от `service="app"` показывает, как этот же ID был успешно подхвачен middleware бэкенда, и фиксирует внутреннее время обработки (`latency_ms: 1`).
* **Ценность:** Если запись от Nginx присутствует (например, со статусом `504 Gateway Timeout`), а от бэкенда по этому ID записей нет — это сигнализирует о том, что бэкенд завис или упал до того, как успел обработать и залогировать входящий контекст.

### Пример 2. Поиск критических падений бэкенда (Перехват паник)
**Сценарий:** В процессе работы бизнес-логики Go-приложения произошло критическое исключение (например, nil pointer dereference). Перехват осуществляется специализированной middleware `Recovery`.

* **Запрос в Grafana (LogQL):**
    ```logql
    {project="deploy", service="app"} |= "panic:"
    ```
* **Результат анализа:** Запрос мгновенно фильтрует логи бэкенда и выводит строки, содержащие информацию о перехваченных паниках и трассировку стека (stack trace).
* **Дальнейшие действия:** Из JSON-пакета упавшего лога извлекается `request_id`, после чего с помощью сквозного поиска (Пример 1) восстанавливается контекст: какой именно клиент, с какими параметрами и на какой конкретно эндпоинт отправил деструктивный запрос.

### Пример 3. Мониторинг сетевых ошибок 5xx на стороне шлюза (Nginx)
**Сценарий:** Контейнер бэкенда полностью остановился, завис или не успевает ответить за таймаут проксирования. При этом бэкенд физически не может записать лог, но инфраструктура должна зафиксировать инцидент.

* **Запрос в Grafana (LogQL):**
    ```logql
    {project="deploy", service="nginx"} | json | status >= 500
    ```
* **Результат анализа:** Конструкция `| json` производит парсинг полей JSON-лога Nginx на лету. Фильтр `status >= 500` оставляет только системные ошибки прокси-сервера (такие как `502 Bad Gateway` или `504 Gateway Timeout`).
* **Ценность:** Позволяет моментально определить «смерть» контейнера приложения или проблемы с сетевой связностью внутри Docker-окружения, когда само приложение «молчит».

### Пример 4. Поиск медленных запросов к API с фильтрацией мусора
**Сценарий:** Необходимо провести оптимизацию производительности и найти «тяжелые» запросы к бизнес-логике (длительностью более 500 мс). При этом требуется очистить выдачу от регулярного спама метрик Prometheus (`/metrics`) и хелсчеков Docker (`/health`).

* **Запрос в Grafana (LogQL):**
    ```logql
    {project="deploy", service="app"} != "/metrics" != "/health" | json | latency_ms > 500
    ```
* **Результат анализа:** * Операторы `!= "/metrics"` и `!= "/health"` исключают из выдачи служебный трафик систем мониторинга, предотвращая забивание лог-панели.
    * Парсер вытаскивает поле `latency_ms` из JSON бэкенда.
    * Фильтр `latency_ms > 500` оставляет только неоптимальные запросы.
* **Ценность:** Помогает выявить «просадки» производительности базы данных, долгие внешние интеграции или неэффективные алгоритмы в хэндлерах бизнес-логики.
